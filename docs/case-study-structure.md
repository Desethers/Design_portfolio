# Case Study Structure

Structure de référence pour les case studies product design du portfolio.

## 01. Contexte

Expliquer le terrain, les utilisateurs, le workflow actuel, les frictions observées et le problème business ou produit.

Cette section doit situer le projet dans un usage réel : qui travaille, avec quels outils, dans quelles contraintes, et pourquoi la situation actuelle crée un problème.

## 02. Reframing

Expliquer comment le problème initial a évolué après recherche, observation ou analyse.

L'objectif est de montrer le déplacement entre le problème apparent et le problème produit plus profond : ce que l'on pensait devoir résoudre au départ, puis ce que l'analyse a révélé.

## 03. Architecture produit

Expliquer la logique produit, les surfaces principales, leurs connexions et les principes de fonctionnement.

Cette section décrit comment le système est organisé : source de vérité, modules, intégrations, flux de données, règles d'interaction et décisions structurantes.

## 04. Expérience produit

Présenter les fonctionnalités clés, les flows, les interactions, les principes d'interface et les moments produit importants.

Cette section doit montrer comment l'architecture devient utilisable : ce que l'utilisateur voit, fait, valide, ajuste ou publie.

## Règles d'usage

- Chaque case study doit suivre ces quatre sections.
- Garder une écriture concise, concrète et orientée produit.
- Éviter les sections UX génériques comme personas, empathy maps ou longs résumés de recherche, sauf si elles servent directement la compréhension du projet.
- Chaque section doit relier les décisions de design à une valeur produit.
- Pour les projets AI-native, décrire explicitement où l'IA transforme le workflow, pas seulement où elle génère du contenu.
- Pour les mockups, se référer en priorité aux composants et écrans existants dans les dossiers Vitreen ou Gallery OS afin de conserver une cohérence produit et visuelle.
